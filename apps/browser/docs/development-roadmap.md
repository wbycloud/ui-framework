## 1. 产品目标与范围

目标是将 browser.uapp 建设成可长期维护的文档与受控网页浏览器，并持续完善 ui-framework 可复用的公共文档能力。首个稳定版本应让用户完成“打开页面、阅读、跟随链接、查找复制、返回原位置、关闭”的完整任务。

优先服务三类内容：

| 内容类别 | 产品承诺 | 验证方式 |
| --- | --- | --- |
| 包内帮助、指南和应用说明 | 无网络也可使用；关键内容和操作完整可达 | 随源码固定页面和真实输入检查 |
| 内部文档及指定来源的资料 | 来源可管理，访问可诊断，支持范围可预期 | 可控 HTTP/HTTPS 页面集及目标页面样本 |
| 经过验证的公开文章、文档和简单 GET 页面 | 按具体阅读任务声明支持；外部网络结果单独记录 | 合法取得的固定样本加公网补充检查 |

继续遵守 C11、公共 C ABI、Lexbor、Light、WinHTTP、WIC 的技术路线。QuickJS-NG 仅服务可信应用界面；远程文档不执行脚本、不提供应用桥。浏览器默认不随宿主启动，不产生后台网页请求，每个实例占用一个宿主标签。

任意现代网站兼容、SPA、复杂登录、持久 Cookie/网页存储、完整多媒体、扩展和同步不属于本路线首个稳定版本的默认范围。后续扩展必须有独立目标与验收，不从“放行一个域名”推导整站兼容承诺。

## 3. 架构分工与源码管理

| 责任层 | 应承担的能力 | 修改边界 |
| --- | --- | --- |
| 宿主 / workspace | 应用入口、标签、加载卸载、实例生命周期、主题和 DPI 通知、线程安全投递 | 保持标准 uapp 路径，不承担网页网络、历史或来源策略 |
| Light 公共文档能力 | 文档解析接入、布局、绘制、输入、选择、查找、滚动、结构化导航及资源事件 | 使用公共 C 接口；可信界面与远程文档持续隔离 |
| browser.uapp | 工具栏、导航、来源设置、网络与重定向、错误提示、会话历史 | 应用逻辑留在应用；网络封装默认不提升为框架通用 HTTP 模块 |
| 构建与验证 | 固定页面、公共调用方、真实输入、预算检查、匹配 SDK、打包及解压复验 | 测试辅助依赖不成为应用运行依赖 |

新工程是应用源码维护入口，框架 `apps/browser` 是自带应用集成位置。M0 先核对两处差异及独有修改，再确定可追溯的同步规则。未经差异审查不能覆盖任何一处；必要时增加最小同步与一致性检查，避免两套代码长期独立演化。

每次公共变更先确认已有等价能力，遵守当时实际版本政策；记录新增接口、生命周期、线程与内存所有权。不无保护改变既有公开结构，不覆盖冻结 SDK。头文件、导入库、DLL 和调用方按同一源码身份交付，并有只用公共 C 接口的验证程序。

### 4.1 M0：可执行的产品基线

建立页面清单，每项至少记录样本 ID、来源类别、输入特征、操作步骤、预期结果、预期简化/拒绝、资源规模和检查入口。

初始样本覆盖包内页、中英文与长文本、编码、链接/片段、图片、列表、宽表格、代码长行、GET，以及错误、超限、慢响应、重定向和隔离输入。复用既有固定服务与测试源码，不重复搭建同类设施。

真实目标站点尚未明确时，以现有固定样本形成可执行基线，将站点选择记录为待决策项；不得据此宣传对任意公开站点的兼容性。

### 4.2 M1：访问策略与网络诊断

来源管理只能由可信应用界面或明确的本地配置入口修改，远程页面不能请求自动放行。设置存储、读取及多实例通知先复用现有公共能力；配置路径应在检查现有合同后确定。

明确包内默认规则、用户配置、恢复默认值和非法配置的优先级。禁止用配置错误回退到全部允许；HTTP/HTTPS、主机和端口继续按规范化 origin 精确匹配。资源和重定向逐次检查；规则修改对在途请求及其他实例的生效时点必须定义并测试。

错误信息至少区分以下情况：

| 类型 | 应展示的信息 | 固定检查 |
| --- | --- | --- |
| 地址或策略拒绝 | 无效 URL、协议、凭据或未允许来源的具体原因 | 非法地址、特殊协议、凭据、相似域名及不同端口 |
| 重定向拒绝 | 原请求与被拒绝目标的关系，说明停止原因 | 同源、跨源、协议变化、循环及次数超限 |
| 子资源失败 | 主文档仍可阅读时标明部分呈现，提供资源失败类别 | 图片/CSS 来源拒绝、损坏、超额及超时 |
| 传输失败 | 连接阶段、系统错误码及可执行的重试/设置入口 | 断网、连接断开、慢响应及超时 |
| TLS 失败 | 保留系统验证结论，说明证书失败 | 未信任证书和授权测试条件下的正向 HTTPS |
| HTTP 或文档失败 | 状态码，或编码、解析、预算、无可读内容的原因 | 404/500、错误编码、空 SPA 及超限 |

核对 WinHTTP 实际使用的系统代理行为及配置获取方式，只实施责任明确的修复。不自动修改系统代理，不降低 TLS 验证，不通过提高超时掩盖公网失败。诊断默认避免输出凭据、表单值、完整敏感查询串和无关网页内容。

M1 交付必须包含使用说明、配置恢复方法、实际构建包与回归证据。无法复现或定位的公网问题保留为未定位项，和本地固定测试结果分开。

### 4.3 M2—M3：按任务扩展能力

每个兼容问题依次判断访问策略、网络、文档能力、交互依赖。先提取最小固定样本，再修改责任层。避免针对网站名称添加不可解释的专用分支。

优先级按“关键操作丢失、正文缺失、阅读受阻、视觉差异”排序。复杂布局能力只有在目标样本证明需要时才增加。对尚不支持的表格合并、列表属性、图片方向等，逐项选择实现或明确简化，不一次性承诺完整标准。

真实 IME、物理 DPI、多屏和辅助技术需要对应环境；缺失时列为未验证，不能用程序 DPI 或合成输入替代。网页作者颜色、可信工具栏主题、窗口 DPI 和页面缩放保持各自语义。

### 4.4 M4—M5：质量和交付

循环与压力测试预先声明样本、次数/时长、停止条件、资源门槛及故障注入方式。观察内存、句柄、线程、回调、请求和队列；关闭检查覆盖初始化/挂载失败、下载/解码中关闭、连续取消及多实例。

性能分别记录网络结束、文本转换、解析、布局、绘制、首段可读和关键资源就绪。每个观察终点都必须能被证据验证；隐藏窗口 paint=0 不代表页面可见。先形成重复测量基线，再讨论优化；流式处理、增量布局和缓存均须由实际瓶颈驱动。

沿用 [当前资源门槛](browser.md#隔离与资源)。确有能力限制时记录影响，不通过增加预算、延长超时或减少样本制造通过。

生产构建持续覆盖测试 OFF、WebView2 OFF、无 Mesa 配置以及应用仅使用匹配 SDK 的构建。新交付使用新的目录或版本身份，保留既有正式归档；每次提供解包检查、实际运行、关闭卸载、进程退出和 SHA。不得假设首版已经验证过就无需验证改后的包。

## 6. 长期能力扩展的决策门槛

若受控文档仍是主要需求，继续沿 M0—M5 改善阅读、可访问性和稳定性。若明确需要动态网页，则先列出目标页面依赖的最小 API、成功任务与资源边界，再做独立可行性验证。

QuickJS-NG 是可嵌入的 JavaScript 引擎。网页脚本平台还涉及 DOM 绑定、事件循环、浏览器 API 和来源模型，因此“启用远程脚本”应单独评估工程量和隔离策略，不能视为现有可信运行时的开关。参见 [QuickJS-NG 官方说明](https://quickjs-ng.github.io/quickjs/)、[HTML Web 应用 API](https://html.spec.whatwg.org/multipage/webappapis.html) 与 [来源模型](https://html.spec.whatwg.org/multipage/browsers.html)。

在开放任意来源或远程脚本前，明确权限边界、执行/内存限制、进程隔离需要、崩溃恢复、网络策略和验证方法。未经新的范围决策，维持远程脚本关闭，也不引入 WebView2、CEF、Electron、Node.js 或其他完整浏览器内核。

## 7. 迭代与验收规则

每批先核对实际代码和政策，建立能失败的检查，再实现最小修改。测试结果须关联源码身份、构建配置、样本和观察终点。

每批交付记录以下六项：

1. 用户可完成的新任务、修复的问题及支持表变化。
2. 应用和框架分别修改了什么，公共 ABI/SDK 是否受影响。
3. 通过、失败、撤回、未定位和未验证项，禁止合并为一个通过数字。
4. 真实输入、资源趋势、取消清理、卸载和退出证据。
5. 构建命令、交付路径、匹配 SDK、源码身份及哈希。
6. 本轮过程产物清理结果；未解决问题仅保留最小诊断材料。

不预设工期。M0 分解任务并确认第一批实际工作量后再估算；范围变化应同步更新计划与风险。
